# Анализ воздушного движения по открытым ADS-B данным

Учебный проект по курсу хранения и обработки данных. Система собирает, хранит, обрабатывает
и анализирует данные о воздушном движении в районе Кейптауна (ЮАР).

Самолёты примерно дважды в секунду передают по радио свои координаты, высоту, скорость и
позывной (стандарт ADS-B). Волонтёрские приёмники по всему миру принимают эти сигналы и
отдают их через открытые API. Из этого потока восстанавливаются траектории и рейсы.

**Регион:** Кейптаун, ЮАР. Аэропорт CPT (FACT), зона примерно 120 x 130 км.
Регион выбран после проверки покрытия: над Россией открытых данных почти не осталось,
над Кейптауном источники видят борты стабильно.

## Источники данных

| Источник | Адрес | Что даёт |
|---|---|---|
| OpenSky Network | `opensky-network.org/api` | позиции бортов, без регистрации 400 запросов в сутки |
| adsb.lol | `api.adsb.lol` | позиции бортов, плюс регистрация и тип самолёта |
| adsb.fi | `opendata.adsb.fi` | позиции бортов, своя сеть приёмников |
| Табло ACSA | `airports.co.za` | расписание и фактические времена рейсов Кейптауна |
| METAR | `aviationweather.gov` | погода в аэропортах: ветер, видимость, облачность |

Три сети приёмников дают разное покрытие, их расхождения сами по себе материал для анализа.
Табло нужно для задержек: в ADS-B есть только факт, расписания там нет. Погода объясняет
выбор посадочной полосы и время захода на посадку.

Данные коммерческих сервисов (FlightRadar24, FlightAware) не используются: их условия
запрещают автоматический сбор.

## Регионы

| Код | Что охватывает |
|---|---|
| `cpt` | Кейптаун и аэропорт CPT, примерно 120 x 130 км |
| `za` | вся ЮАР, бортов в несколько раз больше |

## Структура репозитория

```
collect.py              снимки позиций бортов из трёх источников
collect_board.py        табло аэропорта Кейптауна: расписание и фактические времена
collect_weather.py      сводки METAR по аэропортам ЮАР
summary.py              что уже собрано: таблица по запускам и итоги
tools/coverage_check.py проверка покрытия по регионам, использовалась при выборе Кейптауна
data/                   собранные данные, в репозиторий не попадают (см. .gitignore)
```

## Сбор данных вручную

Сейчас данные собираются руками, два раза в день в течение пяти дней. Оркестрация в Airflow
появится в ЛР1, логика сбора при этом не изменится.

Зависимостей нет, нужен только Python 3.9 и интернет.

### Обычный сеанс сбора

```bash
cd ~/study/data
python3 collect.py --repeat 12      серия из 12 снимков, час работы
python3 collect_board.py            табло за сегодня
python3 collect_weather.py          погода за последние 12 часов
```

Позиции бортов меняются каждую секунду, поэтому их имеет смысл снимать серией: за час
набирается 12 снимков вместо одного. Табло за день меняется медленно, его достаточно
снять один раз за сеанс. Погода выходит раз в час, и запрос сразу забирает историю
за последние 12 часов, так что промежуток между сеансами не теряется.

Полезно делать один сеанс утром и один вечером, чтобы захватить и пик, и затишье.
Кейптаун живёт на два часа раньше Москвы (UTC+2 против UTC+3), то есть 12:00 в Москве
это 11:00 в Кейптауне, а утренний пик вылетов в CPT приходится примерно на 07:00-09:00
по Кейптауну, то есть 09:00-11:00 по Москве.

Что выведет удачный запуск:

```
[1/12] Снимок 20260927T101500Z
  opensky_cpt.json       9 бортов, 4.1 КБ
  adsblol_cpt.json       7 бортов, 18.3 КБ
  adsbfi_cpt.json        7 бортов, 18.0 КБ
  opensky_za.json       34 бортов, 12.1 КБ
  adsblol_za.json       31 бортов, 61.4 КБ
  adsbfi_za.json        30 бортов, 60.2 КБ
Сохранено в data/raw/20260927T101500Z, файлов: 6
```

Если источник не ответил, вместо числа бортов будет строка с ошибкой, а остальные источники
всё равно сохранятся. Серия прерывается по Ctrl+C, уже собранные снимки остаются на месте.

### Другие варианты запуска

```bash
python3 collect.py                          один снимок
python3 collect.py --repeat 12 --interval 120   серия чаще, раз в 2 минуты
python3 collect.py --regions cpt            только Кейптаун, без остальной ЮАР
python3 collect.py --sources opensky        только один источник
python3 collect.py --dry-run                показать запросы, ничего не сохраняя
python3 collect_board.py --date 2026-09-28  табло за другую дату
python3 collect_weather.py --hours 24       погода за сутки
python3 collect_weather.py --airports FACT  только Кейптаун
python3 summary.py                          посмотреть, что уже собрано
```

### Сколько запросов можно делать

У OpenSky без регистрации лимит 400 запросов в сутки, причём большая область стоит дороже
одного запроса. При двух сеансах по 12 снимков выходит около 50 запросов в сутки, запас есть.
У adsb.fi ограничение — не чаще одного запроса в секунду, оно соблюдается в коде.

## Как хранятся снимки

Каждый запуск создаёт свою папку с меткой времени UTC:

```
data/raw/
    20260927T072000Z/
        manifest.json        когда, откуда и сколько забрали
        opensky_cpt.json     ответ OpenSky без изменений
        adsblol_cpt.json     ответ adsb.lol без изменений
        adsbfi_cpt.json
        opensky_za.json
        adsblol_za.json
        adsbfi_za.json
    20260927T181500Z/
        ...
    board/
        20260927T072200Z_cpt.json   рейсы с табло за день
    weather/
        20260927T072300Z_metar.json сводки METAR
```

Ответы источников ADS-B сохраняются как есть, без разбора и правок: в ЛР1 они загружаются
в сырой слой хранилища (ODS), а разбор происходит уже там. `manifest.json` хранит время
запроса, URL, размер ответа, число бортов и ошибку, если она была.

Табло — исключение: сайт отдаёт не JSON, а HTML-страницу на три мегабайта, поэтому
`collect_board.py` разбирает карточки рейсов сразу и сохраняет их списком. В каждом рейсе
есть номер, авиакомпания, направление, время по расписанию, фактическое время, статус,
гейт, стойки регистрации и лента выдачи багажа.

Погода сохраняется как пришла: в каждой сводке ветер, порывы, видимость, облачность,
температура, давление и исходная строка METAR.

Имя папки это время запуска в UTC в формате `ГГГГММДДTЧЧММССZ`. UTC выбран, потому что
в самих данных время тоже в UTC, а часовые пояса Москвы и Кейптауна различаются.

Снимки не коммитятся: они растут каждый день и воспроизводятся повторным запуском.

## План работ

**ЛР1. Airflow и ETL.** Airflow в Docker, три хранилища на выбор, не менее трёх DAG
(позиции бортов, табло аэропорта, погода), загрузка сырых данных в ODS и сравнение хранилищ.

**ЛР2. Обработка.** Слияние источников, чистка выбросов, сборка точек в рейсы, определение
взлёта и посадки, обогащение типом самолёта и авиакомпанией.

**ЛР3. Анализ.** Загрузка аэропорта по часам, длительность захода на посадку, выбор полосы
в зависимости от ветра, доля малой авиации, сравнение покрытия источников.
