# Анализ воздушного движения по открытым ADS-B данным

Учебный проект по курсу хранения и обработки данных. Система собирает, хранит, обрабатывает
и анализирует данные о воздушном движении в районе Кейптауна (ЮАР).

Самолёты примерно дважды в секунду передают по радио свои координаты, высоту, скорость и
позывной (стандарт ADS-B). Волонтёрские приёмники по всему миру принимают эти сигналы и
отдают их через открытые API. Из этого потока восстанавливаются траектории и рейсы.

**Регион:** Кейптаун, ЮАР. Аэропорт CPT (FACT), зона примерно 120 x 130 км.
Регион выбран после проверки покрытия: над Россией открытых данных почти не осталось,
над Кейптауном источники видят борты стабильно.

## Источники данных

| Источник | Адрес | Что даёт |
|---|---|---|
| OpenSky Network | `opensky-network.org/api` | позиции бортов, без регистрации 400 запросов в сутки |
| adsb.lol | `api.adsb.lol` | позиции бортов, плюс регистрация и тип самолёта |

Оба источника открытые и бесплатные. Данные коммерческих сервисов (FlightRadar24, FlightAware)
не используются: их условия запрещают автоматический сбор.

## Структура репозитория

```
collect.py              ручной сбор снимка: опрашивает источники и сохраняет ответы
summary.py              что уже собрано: таблица по запускам и итоги
tools/coverage_check.py проверка покрытия по регионам, использовалась при выборе Кейптауна
data/                   собранные данные, в репозиторий не попадают (см. .gitignore)
```

## Сбор данных вручную

Сейчас данные собираются руками, два раза в день в течение пяти дней. Оркестрация в Airflow
появится в ЛР1, логика сбора при этом не изменится.

### Как запускать

```bash
cd ~/study/data
python3 collect.py
```

Всё. Зависимостей нет, нужен только Python 3.9 и интернет. Запуск занимает несколько секунд.

Полезно делать один запуск утром и один вечером, чтобы в данных были и пик, и затишье.
Кейптаун живёт на два часа раньше Москвы (UTC+2 против UTC+3), то есть 12:00 в Москве
это 11:00 в Кейптауне.

Что выведет удачный запуск:

```
Снимок 20260927T101500Z
  opensky_cpt.json       9 бортов, 4.1 КБ
  adsblol_cpt.json       7 бортов, 18.3 КБ
Сохранено в data/raw/20260927T101500Z
```

Если источник не ответил, вместо числа бортов будет строка с ошибкой, а остальные источники
всё равно сохранятся. В этом случае повторите запуск через несколько минут.

### Другие варианты запуска

```bash
python3 collect.py --dry-run             показать запросы, ничего не сохраняя
python3 collect.py --sources opensky     только один источник
python3 collect.py --regions cpt,za      Кейптаун и вся ЮАР (данных сильно больше)
python3 summary.py                       посмотреть, что уже собрано
```

## Как хранятся снимки

Каждый запуск создаёт свою папку с меткой времени UTC:

```
data/raw/
    20260927T072000Z/
        manifest.json        когда, откуда и сколько забрали
        opensky_cpt.json     ответ OpenSky без изменений
        adsblol_cpt.json     ответ adsb.lol без изменений
    20260927T181500Z/
        ...
```

Ответы сохраняются как есть, без разбора и правок: в ЛР1 они загружаются в сырой слой
хранилища (ODS), а разбор происходит уже там. `manifest.json` хранит время запроса,
URL, размер ответа, число бортов и ошибку, если она была.

Имя папки это время запуска в UTC в формате `ГГГГММДДTЧЧММССZ`. UTC выбран, потому что
в самих данных время тоже в UTC, а часовые пояса Москвы и Кейптауна различаются.

Снимки не коммитятся: они растут каждый день и воспроизводятся повторным запуском.

## План работ

**ЛР1. Airflow и ETL.** Airflow в Docker, три хранилища на выбор, не менее трёх DAG
(позиции, справочник бортов, погода), загрузка сырых данных в ODS и сравнение хранилищ.

**ЛР2. Обработка.** Слияние источников, чистка выбросов, сборка точек в рейсы, определение
взлёта и посадки, обогащение типом самолёта и авиакомпанией.

**ЛР3. Анализ.** Загрузка аэропорта по часам, длительность захода на посадку, выбор полосы
в зависимости от ветра, доля малой авиации, сравнение покрытия источников.
